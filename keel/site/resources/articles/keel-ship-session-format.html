The Keel Ship session format

A Keel Ship session is more than a log. It is a replayable artifact — a plain folder of files that records what an agent did, why it did it, and how to get back to any step.

K By the Keel team · May 21, 2026

On this page

Why record a session

Every time an agent changes a file, someone eventually asks why. A diff shows the result, but it cannot show the reasoning, the detour, or the test that convinced the agent to keep going. We record sessions so that question always has an answer.

A session is not a transcript for its own sake. It is the unit of work that Keel Ship produces: a reproducible, inspectable account of a run, from the first prompt to the last check. Recording it changes how the tool behaves. Because each step will be visible later, the agent works in small steps. Because each approval is logged, you can see exactly where you were asked. And because the session can be replayed, you can revisit a decision without trusting your memory of it.

We also record sessions because agents make mistakes. A run that took a wrong turn is still useful if you can open it, find the step where it went astray, and branch from there. Without a session, the only option is to start again and hope the same mistake does not recur.

This article is a tour of the format: where sessions live, what is inside them, how replay works, and how long-running context stays compact.

The on-disk layout

Sessions live under ~/.keel/sessions in your home directory. Each run gets a folder named for its timestamp and a short slug, so the most recent work sorts to the bottom and nothing overwrites anything. A two-minute task and a two-hour task look the same on disk; only the number of steps differs.

Inside a session folder you will find a manifest, an events log, and a snapshots/ directory. The manifest is a small JSON file with the prompt, the provider, the workspace path, and pointers to the steps. events.jsonl is an append-only list of tool calls, approvals, and check results — one JSON object per line, which makes it easy to search or stream. snapshots/ holds file contents as they stood at each step, stored as compact diffs against the previous snapshot.

Nothing in that folder requires a service. You can copy it to another machine, keep it in a private repository, or delete it when you are done. Because the format is plain text, it stays readable even if the tooling around it changes. Credentials are never written into any of these files.

Scrubbing through a replay

Replay is how you read a session. Running keel ship replay with a session id opens the timeline and lets you scrub — forwards, backwards, or straight to the step where a particular file changed. Scrubbing is more like stepping through a debugger than watching a video: at any point you can see the workspace exactly as it stood then.

Steps that touched only files are deterministic and reproduce byte for byte. Steps that involved the outside world — a package install, an API call, a clock read — are marked in the timeline, with the observed result recorded rather than re-fetched. That distinction keeps replay honest. You can always tell which parts of a run you can re-run exactly and which parts you are reading as history.

You can branch from any step. Add --from with a step number and a new prompt, and a new session is created that shares the earlier history and diverges at that point. The original stays untouched, so exploring an alternative never costs you the run you already trusted.

Context compaction

A long run produces a lot of context. Left unchecked, a session would grow until the useful decisions were buried under tool output. Compaction is how Keel Ship keeps a session readable and affordable as it runs.

After each checkpoint, the session is distilled. Routine tool output is replaced by a one-line result, successful checks collapse to a pass count, and the decisions that shaped the work — what was tried, what was rejected, and why — are promoted into a short note. The full detail stays in snapshots/ and events.jsonl; compaction changes only what the agent carries forward. Nothing is thrown away.

For you, this means a session opens with a readable summary instead of thousands of lines of logs. For the agent, it means a follow-up run starts with the constraints that mattered, not a stale copy of everything it once printed. Compaction runs locally and is itself recorded as a step, so you can see exactly what was condensed and when.

A session should get clearer as it grows, not harder to read. Compaction keeps the decisions and lets the noise fall away.

Working with sessions

Everything above is available from the command line. List recent sessions, pick one, and scrub it step by step:

$ cd ~/projects/atlas-api
$ keel ship sessions --last 3
  2026-05-21-1042-webhook-retry   18 steps · 4 files · checks passed
  2026-05-20-0915-schema-migrate  31 steps · branch available

$ keel ship replay 2026-05-21-1042-webhook-retry --step
  step 4/18  · edit worker/retry.py   · [approved]
  step 5/18  · run pytest -q         · 14 passed
  step 6/18  · compaction note saved

The manifest for that run is ordinary JSON, which makes it easy to inspect or feed into your own tooling:

{
  "id": "2026-05-21-1042-webhook-retry",
  "prompt": "Add retry with backoff to the webhook worker",
  "workspace": "/home/dev/projects/atlas-api",
  "provider": "byok",
  "steps": 18,
  "compacted_at": 14,
  "checks": {
    "command": "pytest -q",
    "passed": 14
  }
}

A practical review loop looks like this:

  1. 1

    Find the run

    Use keel ship sessions --last 5, or open the session list in the desktop app, to locate the work you want to inspect.

  2. 2

    Scrub the timeline

    Step through the changes, paying attention to approvals and to anything marked as an outside-world call. Open a snapshot when you want the exact file state.

  3. 3

    Branch a decision

    If a choice looks wrong, branch from that step with a new instruction. The original session remains intact for comparison.

  4. 4

    Keep or discard

    Merge the result you trust, archive the session with the pull request, or delete it once it has served its purpose. Nothing about the format requires it to live forever.

Tip

Treat a session like a code review, not a recording. You rarely need to watch every step — jump to the approvals, the checks, and the first snapshot that looks surprising. That is usually where the interesting decisions live.

Availability

The session format ships with Keel Ship and Keel Code today. Update your Keel installation and the keel ship replay command group is ready immediately; the desktop app opens the same sessions as a visual timeline. No hosted service is required, and every session can be replayed offline.
