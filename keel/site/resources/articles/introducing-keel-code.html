Introducing Keel Code

Keel Code is the terminal-native agent that pairs with you on real work — reading your workspace, respecting your boundaries, and leaving a session you can replay.

K By the Keel team · May 21, 2026

On this page

A partner in the terminal

Keel Code is a terminal-native agent that pairs with you on real work. It is not a chat window that happens to mention your repository — it is a collaborator that lives in the same shell where you already build, test, and ship.

Most coding assistants wait to be told exactly what to do. Keel Code starts by understanding where you are. It reads the files in front of you, the tests you run, and the conventions your team has already agreed on. Then it works in small, visible increments, pausing at the moments that matter so you stay in charge.

That pairing is the point. You keep the decisions; Keel Code keeps the typing. When a task is mechanical — a rename across twenty files, a migration, a test for an awkward edge case — it moves quickly. When a task is ambiguous, it asks, proposes a short plan, and waits for a yes. Every step lands in a session you can inspect later, so the work never disappears into a stream of scrollback.

Today we are opening Keel Code to everyone. This article walks through how it reads a project, where the permission gates sit, how to bring your own provider, and what a replayable session makes possible.

Reading your workspace

Every run begins with a read. Keel Code walks the workspace the way a new teammate would: the README, the package manifests, the test configuration, the instruction files your team keeps in the repo, and the code around the file you mentioned. It respects ignore rules and symlinks in the same way your existing tooling does, so generated output and secrets stay out of the picture.

From that reading it builds a compact model of the project — which commands are safe to run, how the pieces fit together, and what “done” looks like for the change you asked for. Because the model is rebuilt from the workspace each time, it does not go stale the way a pasted summary does. Change a test command on Tuesday and Keel Code sees the new one on Wednesday.

You can scope that reading precisely. Point it at a single directory, hand it a specific file, or tell it to stay inside a worktree. The narrower the scope, the smaller the blast radius, and the easier it is to review what came back. For larger tasks, Keel Code reads broadly but still proposes one change at a time, so you can watch the direction before it commits to a path.

Permission gates and your own keys

An agent that can edit files and run commands needs boundaries. Keel Code ships with permission gates that are explicit, local, and under your control. Reads are allowed by default. Edits to files in the working tree are shown as a proposed patch before they are applied. Commands that touch the network, install packages, or leave the project directory require a clear yes.

Those gates are not a single on/off switch. You can allow a whole category for the length of a run, approve one action once, or deny it and move on. Denials are remembered in the session, so the agent does not ask again about something you already refused. If you want a faster loop for a trusted task, you can grant a broader scope for that session only — and it resets when the session ends.

Providers are yours to choose. Keel Code supports bring-your-own-key: point it at the provider you already use, supply your own credentials, and set your own spending limits. Credentials are stored locally and encrypted at rest, never written into a session or a prompt. Nothing is sent to a service you have not configured, and the whole workflow functions without a hosted account.

Sessions you can replay

Every Keel Code run is recorded. A session is an ordered artifact: the prompt you gave, the context that was read, each proposed change, each tool call and its arguments, the checks that ran, and the moment you approved or denied something. It is replay in the most practical sense — you can open a finished run and step through it rather than guessing from a diff.

That record has immediate uses. Review a run before you merge. Hand a teammate the exact sequence that produced a surprising result. Branch from an earlier step with a corrected instruction instead of starting over. Sessions are plain files on your machine; they work offline and they survive a change of provider.

Because Keel Ship uses the same session format, a run you start in the CLI continues cleanly in the desktop app. The surface changes; the artifact does not.

Getting started with keel code

Getting started takes a terminal and a repository. Install Keel Code, open a shell in your project, and run keel code. The CLI checks the workspace, shows which provider is active, and waits for your first instruction.

$ cd ~/projects/atlas-api
$ keel code
  Keel Code · workspace: atlas-api · provider: your-key

> Add retry with backoff to the webhook worker
  read   12 files · plan: 3 steps
  edit   worker/retry.py           +18 -2   [approved]
  run    pytest -q tests/test_webhook.py    14 passed
  session saved → ~/.keel/sessions/2026-05-21-1042.json

From there, a short loop is enough for most tasks:

  1. 1

    Verify the install

    Run keel --version to confirm the CLI is on your path, then open a terminal at the root of the repository you want to work in.

  2. 2

    Connect a provider

    Add your own key with keel code model --set, or stay on the local default. Credentials never enter a session file.

  3. 3

    Start the session

    Run keel code and describe one change in a sentence. Review each proposed patch and approve, deny, or edit the plan as it goes.

  4. 4

    Read the session

    Use keel code sessions --last 5 to find recent runs, then step through the one you just finished before you merge anything.

A little preparation makes the first run much smoother:

  • A repository with a readable README and a test command the agent can discover.
  • A provider key of your own, or the local default model.
  • A clean branch or worktree you are comfortable letting the agent edit.
  • A few minutes at the end to read the session before you merge.
Tip

Start with one small, checkable task — a single bug, one migration, one test made green. Keel Code is at its best when a run has a clear finish line. Once you trust the loop, chain several short sessions together.

Availability

Keel Code is available today on macOS, Linux, and Windows as part of the Keel download. Install the CLI to work from the terminal, or use the desktop app when you would rather watch a visual timeline of each step — both share the same session format, so moving between them costs nothing.

Runs are local by default. Your repository, your sessions, and your credentials stay on your machine, and you choose which provider Keel Code uses and what it is allowed to touch. See the product page for the full command reference, or check system requirements before you install.
