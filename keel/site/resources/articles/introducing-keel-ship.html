Introducing Keel Ship

Announced today, Keel Ship is an agentic coding tool designed to work alongside you in the terminal.

K By the Keel team · May 21, 2026

On this page

Introduction The Keel Code subagent Replaying sessions Preserving context How to use Keel Ship Availability

A build log you can run again

When we set out to make Keel Ship, we gave the team an unusually strict brief: build a tool that could explain every decision it made, replay every step, and hand off cleanly to a human at any moment. The result is an agentic coding tool that lives in your terminal and treats the work itself — not just the final diff — as the artifact.

Keel Ship was built, in large part, by Keel Code. We pointed the Keel Code subagent at the same repositories our customers work in and asked it to ship small, well-scoped changes: a parser fix, a flaky test, a migration script. Each run produced a session — an ordered record of prompts, tool calls, file edits, and the occasional careful revert. Those sessions became the raw material for Ship.

That origin story matters. It is why Keel Ship feels less like a chat window bolted onto a shell and more like a careful teammate who writes things down. It reads your repository, proposes a short plan, works in small increments, and leaves behind a trail you can inspect, branch, and replay. The change is useful on its own; the record of how it was made is what makes it trustworthy.

Today we are opening Keel Ship to everyone. This article walks through how it works, what a replayable session looks like, how context survives across runs, and the two ways you can start using it in your own projects.

The Keel Code subagent

Under the hood, Keel Ship is a thin, opinionated interface around Keel Code. When you start a run, Ship spawns a dedicated Keel Code subagent with a narrow task and a deliberately bounded set of tools: read files, edit files, run commands in a sandbox, and report back. It does not get to rewrite your whole repository on a whim.

The subagent works in a loop. It reads the relevant files, forms a short plan, makes one change, runs the smallest useful check, and then decides whether to continue. Because the loop is small and observable, you can interrupt it, redirect it, or take over completely without losing the work already done. Nothing is hidden behind a long, unbroken stream of output.

We built it this way for a practical reason. Long, uninterrupted agent runs are hard to trust. Short, well-instrumented ones are easy to review. Keel Code supplies the reasoning; Keel Ship supplies the structure — checkpoints, budgets, and an explicit stop condition for every task. When a run finishes, you know exactly which files changed and which checks ran.

The same subagent powers Keel Code in the CLI, so a run you begin in the terminal can be continued in the desktop app, and vice versa. The session format is shared between the two surfaces; only the way you look at it changes.

Replaying sessions, not just diffs

A diff tells you what changed. It rarely tells you why. Keel Ship stores each run as a session artifact: a compact, ordered log of the prompt, the plan, each tool call with its arguments, the resulting file snapshot, and the checks that ran in between. Think of it as a build log that you can step through like a debugger.

You can open a session after the fact and replay it one step at a time. Replay is deterministic for file operations and clearly marked where the outside world was involved — a package install, an API call, a clock read. That distinction makes sessions useful for debugging a surprising result, for reviewing a teammate's change, and for showing a new contributor how a particular decision was reached.

Sessions are plain files. They live in your project under .keel/sessions/ and can be committed, reviewed in a pull request, or discarded. Nothing about them requires a hosted service, and nothing about them locks you into a particular editor.

# List the most recent sessions recorded for this repository
keel ship sessions --last 5

# Replay a session step by step in the terminal
keel ship replay 2026-05-21-1042 --step

# Branch a session and continue from step 4 with a new instruction
keel ship replay 2026-05-21-1042 --from 4 --prompt "Keep the API stable"

Preserving context across runs

The hardest part of agentic work is not the first run — it is the second. A tool that forgets everything between invocations turns every follow-up into a fresh explanation, and every fresh explanation is another chance to lose an important constraint. Keel Ship carries context forward in three layers.

First, the repository is the source of truth. Keel Ship reads project instructions, code, and tests directly, so it does not rely on a stale summary someone pasted into a prompt. Second, each session records a compact decision note: what was attempted, what worked, and what was deliberately left undone. Third, when you branch a session, the subagent starts with the earlier decision notes attached, so constraints you set on Monday still hold on Thursday.

The result is that “continue where you left off” actually means something. You can close your laptop, come back the next morning, and ask Keel Ship to pick up a migration exactly where it paused — including the reasoning behind the choices it already made. If you disagree with one of those choices, you can branch from that step instead of starting over.

Context is not a blob of text you carry between runs. It is a set of decisions you can point to, question, and reverse.

Two ways to get started

Keel Ship runs wherever you work. You can drive it entirely from the Keel Code CLI, or use the Keel desktop app when you would rather watch a visual timeline of each step. Both share the same session format, so moving between them costs nothing — and neither requires you to change how your project is organized.

  1. 1

    Quick start

    Update Keel Code to the latest version, open a terminal in your repository, and run keel ship init. Ship creates a .keel/ directory for session data and checks that it can find your test command.

  2. 2

    Start a run

    Describe one change in a sentence. The Keel Code subagent plans the work, makes the edit in small steps, and stops when the checks pass — or when it needs your input.

  3. 3

    Review and continue

    Open the session timeline in the terminal or the desktop app, step through the decisions, and either merge the result or branch the session with a follow-up instruction.

$ cd ~/projects/keel-web
$ keel ship init
  Keel Ship ready · sessions will be stored in .keel/sessions/

$ keel ship "Add retry with backoff to the webhook worker"
  Keel Code subagent started (task: webhook retry)
  4 files changed · 12 checks passed · session saved

$ keel ship replay latest --step

Before you begin, it helps to have a few basics in place:

  • A repository with a readable README and a test command Ship can discover.
  • Keel Code installed and signed in — the account is local unless you choose otherwise.
  • A quiet branch or worktree that you are comfortable letting the subagent edit.
  • Five minutes at the end to read the session before you merge anything.
Tip

Start with a task small enough to describe in one sentence. Keel Ship is at its best when a run has a clear finish line — a single bug, one migration, one test suite made green. Once you trust the loop, chain several small runs together.

Availability

Keel Ship is available today alongside Keel Code. If you already use the Keel desktop app, update to the latest version and Ship appears in the sidebar. If you work in the terminal, update Keel Code and the keel ship command group is ready immediately. The two surfaces share sessions, so you do not have to pick a home.

Keel Ship runs locally by default. Your repository, your sessions, and your decision notes stay on your machine; you choose which model provider Keel Code uses and what it is allowed to touch. Nothing is sent anywhere you have not configured, and every run can be replayed offline.
