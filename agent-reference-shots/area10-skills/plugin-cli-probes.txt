# Area 10 - plugin CLI surfaces and the validator contract (OBSERVED-CLI)

All commands were run against throwaway probe plugins under the system temp dir
with `CLAUDE_CONFIG_DIR` pointed at a scratch config dir, so the real
`~/.claude/plugins` install records were never touched.

## P1 - `claude plugin list --json`

    $ claude plugin list --json
    [
      {
        "id": "probe-scaffold@skills-dir",
        "version": "0.1.0",
        "scope": "user",
        "enabled": true,
        "installPath": "<SCRATCH_CFG>\\skills\\probe-scaffold"
      }
    ]

A skill folder that carries a `.claude-plugin/plugin.json` is registered as a
plugin whose id is `<name>@skills-dir`, and it is reported with an explicit
`scope` and an `installPath`.

## P2 - `claude plugin details <id>` (component inventory + token cost)

    $ claude plugin details probe-scaffold@skills-dir
    probe-scaffold 0.1.0
      Description: Scaffold probe plugin
      Source: probe-scaffold@skills-dir

    Component inventory
      Skills (1)  example
      Agents (1)  example
      Hooks (0)
      MCP servers (0)
      LSP servers (0)

    Projected token cost
      Always-on:   ~69 tok   added to every session

    Per-component (rounded)
      component  always-on  on-invoke
      example          ~50       < 20
      example         < 20       < 20

      On-invoke cost is paid each time a skill or agent fires.
      Token counts are estimates and may differ from actual usage.

The tool distinguishes the always-on cost (the description the model sees every
turn) from the on-invoke cost (the body, paid only when the skill/agent runs).

## P3 - `claude plugin validate --json` on a plugin manifest

Envelope shape:

    {
      "success": true,
      "strict": false,
      "target": "<path>",
      "manifest": { "file": ..., "type": "plugin",
                    "errors": [], "warnings": [], "notes": [], "gatingHooks": [] },
      "contents": [],
      "advice": [],
      "directory": { "profile": null, "findings": [ ... ], "undecided": [],
                     "incomplete": false, "failure": null, "notes": [] }
    }

`contents` entries are per-file records:

    { "file": ..., "type": "skill",
      "errors":   [ { "path": ..., "message": ..., "code": null } ],
      "warnings": [ { "path": ..., "message": ..., "code": null } ],
      "notes": [], "gatingHooks": [] }

`directory.findings` entries:

    { "code": "README_MISSING", "title": "README missing", "severity": "error",
      "blocking": true, "hold": false, "file": "README.md", "field": "",
      "message": ..., "fix": ... }

Codes observed: `README_MISSING`, `LICENSE_MISSING`, `ICON_MISSING`.

## P4 - `claude plugin validate` on a skills directory (no manifest)

    $ claude plugin validate <PROJ>/.claude/skills
    Validating components in: <PROJ>\.claude\skills

    ✔ Validation passed

    $ claude plugin validate <PROJ>/.claude/commands
    ✘ Found 1 error:
      ❯ directory: No manifest found in directory. Expected
        .claude-plugin/marketplace.json or .claude-plugin/plugin.json
    ✘ Validation failed

So the same command validates a *components* directory when the path points at a
skills folder, and a *manifest* when the path points at a plugin root. The
distinguishing factor observed here was the presence of a `.claude/skills`
directory in the target.

## P5 - Skill-level validation results

Fixture: skill with no `description` in frontmatter.

    "success": true, "strict": false,
    "contents": [ { "file": ".../bad-skill/SKILL.md", "type": "skill",
      "errors": [],
      "warnings": [ { "path": "description",
        "message": "No description in frontmatter. A description helps users and Claude understand when to use this skill.",
        "code": null } ],
      "notes": [], "gatingHooks": [] } ]

Fixture: skill whose frontmatter YAML does not parse.

    "success": false, "strict": false,
    "contents": [ { "file": ".../yaml-skill/SKILL.md", "type": "skill",
      "errors": [ { "path": "frontmatter",
        "message": "YAML frontmatter failed to parse: YAML Parse error: Unexpected EOF. At runtime this skill loads with empty metadata (all frontmatter fields silently dropped).",
        "code": null } ],
      "warnings": [], "notes": [], "gatingHooks": [] } ]

Fixture: skill with no frontmatter block at all.

    "success": true, "strict": false,
    "contents": [ { "file": ".../nofront/SKILL.md", "type": "skill",
      "errors": [],
      "warnings": [ { "path": "frontmatter",
        "message": "No frontmatter block found. Add YAML frontmatter between --- delimiters at the top of the file to set description and other metadata.",
        "code": null } ],
      "notes": [], "gatingHooks": [] } ]

Fixtures that produced NO findings (i.e. `contents: []`): a skill with every
Agent-Skills-spec field set, a skill in a folder named `synced`, a skill with
`context: fork` / `agent:` / `paths:`, and a skill with an unknown frontmatter
field (`descripton:`). The validator therefore checks *presence and parseability*
of the frontmatter, not the correctness of individual field values.

Note: the human-readable output of the same run said `✔ Validation passed` even
though the JSON envelope's `success` was `false` for the bad-YAML case, and the
`--strict` flag (documented as "treat warnings as errors") is what turns the
non-fatal warnings into a non-zero exit.

## P6 - `claude plugin validate` on a plugin root (human-readable)

    $ claude plugin validate <PROJ>
    Validating plugin manifest: <PROJ>\.claude-plugin\plugin.json

    Plugin directory checks for <PROJ>. The plugin directory is the catalog that
    plugins are submitted to; this is a subset of what it runs.

    ✘ Found 1 problem the plugin directory refuses a submission for:

      ❯ README.md: README missing (README_MISSING). ...
        Fix: Add a README.md to the plugin folder describing what the plugin
        does, how to use it, and any setup it needs, in at least 40 words. ...

    ⚠ Found 1 plugin directory warning:

      ❯ .claude-plugin/plugin.json icon: No icon (ICON_MISSING). ...
        Fix: Add a square PNG to the plugin folder at .claude-plugin/icon.png, or
        set `icon` in plugin.json to the path of a square PNG or JPEG in the
        plugin: 512 to 2048 px on each side, under 2 MB. ...

    These plugin directory checks do not change the result below. To fail on
    problems the directory refuses a submission for, run this command with
    --profile directory.

    The directory also runs a safety scan and a policy review that this command
    does not.

    ✔ Validation passed

The last two sentences are an important product behaviour: the local validator
reports directory-submission findings but does not enforce them, and it says so
explicitly.

## P7 - `claude plugin init` component list

    $ claude plugin init --help
    Usage: claude plugin init|new [options] <name>

    Scaffold a new plugin at ~/.claude/skills/<name>/ (auto-loads next session as
    <name>@skills-dir)

    Options:
      --author <name>         Author name (default: git config user.name)
      --author-email <email>  Author email (default: git config user.email)
      --description <text>    Manifest description
      -f, --force             Overwrite an existing .claude-plugin/ at the target
      -h, --help              Display help for command
      --with <components...>  Also scaffold: skills, agents, hooks, mcp, lsp,
                              output-style, channel

Observed: `--with skills agents commands` is rejected with
`✘ Unknown --with component "commands". Valid: skills, agents, hooks, mcp, lsp,
output-style, channel` - legacy `commands/` is not a scaffoldable component in
this build, even though the runtime still loads legacy command files.

## P9 - `claude agents --json` (background-session registry, not agent definitions)

    $ claude agents --json
    []

    $ claude agents --help
    Usage: claude agents [options]
    Manage background agents
    ...
      --json   Print active sessions (interactive and background) as a JSON array
               and exit (for scripting; does not require a TTY)

`claude agents` lists BACKGROUND SESSIONS, not subagent definitions. The
subagent definitions live in `init.agents` in the session init event.

## P10 - `claude import` is not available in this build

    $ claude import --dry-run <something>
    `claude import` is not yet available in this build.

This contradicts the published documentation's description of the command; see
the finding entry in the report.
