## 1. Actual supported upgrade/rollback mechanism (read from shipped code)

| Stage | Real code path | Behaviour confirmed |
| --- | --- | --- |
| Update discovery | `keel/src/keel/release/updater.py:check_for_update` (`load_manifest` → optional Ed25519 manifest verification → newest-version selection, `min_version`, `blocked_versions`, rollout bucket) | A signed manifest's `files` entry is selected for the running platform; older/equal versions are ignored. |
| Verified download | `updater.download_update` via `release/verify.py:fetch_bytes` | HTTPS-only (loopback HTTP only with `allow_http`), `Content-Length` check, SHA-256 check, optional detached Ed25519 `.sig` check, atomic temp-file replace. |
| Atomic swap | `updater.atomic_install(staged_dir, install_dir, backup_dir)` | `install → backup`, `staged → install`; on failure of the second rename it restores `backup → install`. |
| Failed-start detection | `keel/src/keel/start_health.py:record_start` | Consecutive failed starts for a version; `rollback: true` at 3 (default `DEFAULT_THRESHOLD=3`); a successful start resets the counter. The caller must then invoke `updater.rollback` — this is the documented recovery contract (`WINDOWS-EXTERNAL-VALIDATION.md:79-81`). |
| Recovery | `updater.rollback(install_dir, backup_dir)` | Removes the bad install, renames the known-good backup into place; refuses if no backup dir exists. |

This is a **directory-swap installer/updater**, not an in-place package manager. User data is expected to live outside the install directory (the app's `~/.keel` user-data model). The drill mirrors that: the install directory is swapped; a real SQLite user-data file lives in a sibling `userdata/` directory and must survive untouched.

Documentation cross-check: `PRODUCTION-READINESS-MATRIX.md:26,34`, `FINAL-RELEASE-OPERATIONS.md:241-249` (external check 5: "install 0.1.0 then 0.1.1; force 3 failed starts; verify rollback"), `WINDOWS-EXTERNAL-VALIDATION.md:71-81`.

### 3.1 What each drill step proves

| Task | Evidence |
| --- | --- |
| Simulate installed 0.1.0 and upgrade via real updater | Baseline app starts and prints `KEEL_APP_VERSION=0.1.0`; real `check_for_update` returns plan `0.1.1` from the signed loopback manifest; real `download_update` verifies size, SHA-256 and detached Ed25519 signature; real `atomic_install` makes 0.1.1 active and preserves 0.1.0 as `backup`. |
| Force N failed starts as the updater expects | Three real subprocess starts of the upgraded build return `rc=1`; real `start_health.record_start` returns `rollback_flag=False, False, True` with `failures=1,2,3`. |
| Automatic rollback to known-good; app starts again | Real `updater.rollback` restores `0.1.0`; backup directory is gone; the app starts again with `KEEL_APP_VERSION=0.1.0` and exit 0; a subsequent healthy start is recorded with `rollback=False`. |
| DB state preservation | A real SQLite 3.45.1 file (`keel.sqlite3`, table `notes`, row `id=1`) sits in `userdata/` outside the swapped install dir. Canary `upgrade-rollback-canary` is read before upgrade, after upgrade, and after rollback — byte-identical row in all three states. |
| Fail-closed: corrupt manifest | Tampered signed manifest (`version` changed after signing) and syntactically invalid JSON both raise `updater.UpdateError`; install remains 0.1.0, no backup, no download. |
| Fail-closed: missing artifact | Signed manifest is valid and yields a plan, but the artifact URL returns HTTP 404; `download_update` raises `urllib.error.HTTPError`, no destination file is written, install remains 0.1.0 and starts. |
| Fail-closed: interrupted upgrade | Two variants: (a) real truncated transfer (server declares `Content-Length` larger than bytes it sends) makes real `fetch_bytes`/`download_update` raise `RuntimeError: Content-Length ... != downloaded ...`; no file written; (b) real `atomic_install` interrupted by a Windows directory lock between the two renames raises `PermissionError` and its own compensation restores `0.1.0` — app starts, SQLite intact. No bricked state in either case. |
| No spurious rollback | A separate regression test upgrades to a healthy 0.1.1, records 3 successful starts, and confirms `rollback` is never flagged and the app stays 0.1.1. |

All six tests are in `keel/tests/test_prod_upgrade_rollback.py`; no production
keys, paid services, network egress or frontend code are used.
